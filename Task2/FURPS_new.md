## Таблица требований в формате FURPS+ (MVP Открытие Депозитов)

| Код | Требования | Архитектурно-значимое | Комментарий |
| :--- | :--- | :--- | :--- |
| F | Функциональные (Functionality) | | |
| F.1 | Сайт. Подача заявки на депозит новым клиентом (Ф.И.О., телефон). | Нет | Заявка передается в Систему кол-центра. |
| F.2 | Система кол-центра. Просмотр/обработку заявок с Сайта и возможность предложить особые условия. | Нет | |
| F.3 | Интернет-банк. Отображение клиенту актуальных персонализированных ставок. | Да | Требует безопасной интеграции с новым источником расчета ставок. |
| F.4 | Интернет-банк. Подача заявки на депозит (указание счета/суммы). | Нет | |
| F.5 | Обеспечить возможность работы со ставками для сотрудников бэк-офиса депозитов и бэк-офиса кредитов. | Да | Требует реализации единого сервиса ставок (F.8) с механизмом контроля доступа. |
| F.6 | АБС. Функционал подтверждения условий депозита и открытия депозита менеджером бэк-офиса. | Нет | |
| F.7 | Интернет-банке. Подтверждение операции открытия депозита  с помощью СМС-кода. | Нет | Необходимо использовать существующий СМС-шлюз, избегая доработок подрядчика. |
| F.8 | (Доп.) Реализовать Сервис Расчета Ставок (СРС), как единый источник актуальных и персонализированных ставок. | Да | Позволит разгрузить АБС и централизовать логику, вынесенную сейчас в XLS-файлы. |
| U | Удобство использования (Usability) | | |
| U.1 | Интерфейс должен быть максимально удобным для клиента. | Нет | Общее требование к UX/UI. |
| U.2 | Придерживаться принятой в компании системы дизайна и брендированных элементов. | Нет | Обеспечение узнаваемости и консистентности. |
| R | Надёжность (Reliability) | | |
| R.1 | Все сервисы должны работать 24/7 и быть доступны в 99,9% случаев. | Да | Требует дополнительные мощности и прочие  механизмы отказоустойчивости. |
| R.2 | Обеспечить доступность сервисов интернет-банка при сбоях в основном ЦОД. | Да | Необходимо реализовать механизм распределения нагрузки, так как текущая команда заявляет о невозможности выполнения требования. |
| P | Производительность (Performance) | | |
| P.1 | Отклик по всем операциям должен занимать менее секунды. | Да | |
| P.2 | Обеспечить равномерное горизонтальное масштабирование и распределение запросов между серверами. | Да | Требует вынесения логики из АБС (вертикальное масштабирование) в масштабируемые сервисы. |
| P.3 | Избежать прямой работы Интернет-банка с API АБС. | Да | Необходимость, вызванная перегрузкой базы данных АБС и требованием 24/7. |
| S | Сопровождаемость (Supportability) | | |
| S.1 | Использовать технологии, на которые уже есть экспертиза в банке (Java, React, PostgreSQL, MS SQL, Oracle). | Нет | Оптимизация затрат и скорости разработки, снижение зависимости. |
| S.2 | Предусмотреть разработку документации для дальнейшего расширения системы. | Нет | |
| + | Архитектурные требования (Architectural) | | |
| A.1 | Обеспечить шифрование трафика (SSL/TLS) для всех каналов (Сайт, Интернет-банк), передающих чувствительную информацию. | Да | Базовое требование безопасности. |
| A.2 | Ввести интеграционный слой (API Gateway) между Интернет-банком и АБС для асинхронной связи. | Да | Решение для обхода перегрузки АБС (P.3) и обеспечения горизонтального масштабирования (P.2). |
| A.3 | Рассмотреть перевод части функционала Интернет-банка на микросервисную архитектуру в рамках этой задачи. | Да | Решение для обеспечения совместимости с Kafka (А.4) и повышения масштабируемости. |
| A.4 | Ввести очередь сообщений (Kafka) для асинхронной передачи данных (заявки, СМС). | Да | Требование на перспективу для повышения отказоустойчивости и скорости отклика (P.1). |
| A.5 | (Доп.) Ввести единый Сервис Идентификации Клиентов (IDP) для централизованной аутентификации. | Да | Повышение безопасности, упрощение авторизации и снижение дублирования учетных данных. |
| A.6 | (Доп.) Обеспечить механизм журналирования (логирования) всех транзакций для целей аудита и отладки. | Да | Критически важно для финансовых операций и выполнения требований надежности (R.1). |
