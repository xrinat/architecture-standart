### **Функциональные требования**

| **№** | **Действующие лица или системы** | **Use Case** | **Описание** |
| :---: | :--- | :--- | :--- |
| 1 | Клиент (Новый), Сайт, Система кол-центра | Подача заявки новым клиентом | Новый клиент оставляет Ф.И.О. и телефон на **Сайте**. Данные передаются в **Систему кол-центра** для обработки менеджером. |
| 2 | Клиент (Существующий), Интернет-банк, Сервис Расчета Ставок (СРС) | Получение персонализированной ставки | Клиент входит в **Интернет-банк**. Интернет-банк запрашивает **СРС** для отображения актуальных персонализированных ставок. |
| 3 | Клиент (Существующий), Интернет-банк, АБС, СМС-шлюз | Открытие депозита онлайн | Клиент выбирает счет/сумму и подает заявку в **Интернет-банке**. Операция подтверждается **СМС-кодом**. |
| 4 | Менеджер бэк-офиса, АБС, СРС | Обработка и подтверждение заявки | Менеджер бэк-офиса обрабатывает заявку, используя **АБС** и **СРС**. СРС предоставляет единую логику расчета ставки. Менеджер подтверждает условия в АБС. |
| 5 | АБС, СМС-шлюз | Оповещение об открытии | После подтверждения ставки и открытия депозита, **АБС** (через ИТ-команду) отправляет **СМС-уведомление** клиенту. |

### **Нефункциональные требования**

| **№** | **Требование** |
| :---: | :--- |
| NF.1 | **Надёжность:** Доступность сервисов **24/7** и **99,9%**. Переключение на резервный ЦОД при сбое. |
| NF.2 | **Производительность:** Отклик в **миллисекундах**. Сервисы должны выдерживать требуемую нагрузку. |
| NF.3 | **Масштабирование:** Обеспечить **горизонтальное масштабирование** нового функционала. |
| NF.4 | **Безопасность:** Шифрование трафика (SSL/TLS) для всех каналов, передающих чувствительную информацию. |
| NF.5 | **Интеграция:** **Избежать прямой работы** Интернет-банка с API перегруженной АБС. Использовать совместимые технологии. |
| NF.6 | **Сопровождаемость:** Использовать внутреннюю экспертизу, избегать доработок подрядчика. |
| NF.7 | **Разгрузка АБС:** Снизить нагрузку на перегруженную базу данных АБС. |

**Описание основных компонентов и интеграций:**

| Компонент | Технология | Назначение и Интеграция |
| :--- | :--- | :--- |
| **Интернет-банк (Frontend)** | ASP.NET MVC, .NET 4.5 | Канал для существующих клиентов. Связь с **API Gateway**. |
| **API Gateway / Service Bus** | **Новый (Java/Spring Boot)** | **Интеграционный слой (NF.5).** Обеспечивает защищенный доступ к новым сервисам. Передает запросы на ставки в **СРС** и заявки в **СОЗ**. |
| **Сервис Расчета Ставок (СРС)** | **Новый (Java/Spring Boot, PostgreSQL/MS SQL)** | **Централизация логики ставок (F.8).** Предоставляет актуальные персонализированные ставки. Получает данные о риске из АБС. |
| **Сервис Оркестрации Заявок (СОЗ)** | **Новый (Java/Spring Boot, Kafka)** | Управляет **асинхронным** потоком заявки (NF.7). Принимает заявки из API Gateway и передает команды на запись в АБС. |
| **АБС (Core Banking)** | Delphi, Oracle | Финальное подтверждение и открытие депозита (F.6). Является **источником данных о риске**. |
| **Система кол-центра** | React.js, Java Spring Boot | Обрабатывает заявки новых клиентов с Сайта. |

#### **Логика и Обоснование Принятия Решений**

1.  **Перегрузка АБС (NF.7, NF.5):** Внедряются *API Gateway* и *Сервис Оркестрации Заявок (СОЗ)* с использованием **Kafka** (A.4). Это предотвращает прямые синхронные вызовы от высоконагруженных каналов к АБС, обеспечивая асинхронную обработку и защиту базы данных АБС.
2.  **Ручной расчета ставок (F.5, F.8):** Создан *Сервис Расчета Ставок (СРС)* на *Java/Spring Boot* (используется существующая экспертиза – NF.6). СРС вынесен в отдельный контейнер, что позволяет ему **горизонтально масштабироваться** (NF.3, P.2).
3.  **Нефункциональные требования (NF.1, NF.2):** Использование микросервисной архитектуры для новых компонентов (СРС, СОЗ, Gateway) на стеке Java обеспечивает **высокую доступность (24/7)**, **быстрый отклик (> секунды)** и поддержку требований **резервного ЦОД** (NF.1).
4.  **Технологический стек (NF.6):** Выбран стек *Java/Spring Boot* и *PostgreSQL/MS SQL*, поскольку в банке есть экспертиза в Java-стеке, и это совместимо с существующими платформами.

### **Альтернативы**

| Альтернативное Решение | Причина Отклонения |
| :--- | :--- |
| **Написание новой микросервисной архитектуры** | **Опасное дейстиве** на этом этапе. Долгое проектирование и моделирование текущих процессов. Опасность долгой разработки без учётов рисков. |
| **Прямое взаимодействие (Интернет-банк $\rightarrow$ API АБС)** | **Противоречит NF.5 и NF.7.** Приведет к немедленной перегрузке базы данных Oracle в АБС и не выполнит требования к доступности 99,9% и масштабированию. |
| **Реализация логики ставок внутри АБС (PL/SQL)** | **Противоречит NF.3 и P.2.** АБС масштабируется только вертикально, что не позволит добиться требуемого **горизонтального масштабирования** и высокой производительности при росте числа клиентов. |


### **Недостатки, ограничения, риски**

| Тип | Описание | Пути Снижения Рисков |
| :--- | :--- | :--- |
| **Ограничение** | **Вертикальное масштабирование АБС.** База данных АБС остается узким местом для всех операций, требующих обращения к ядру. | Разгрузка АБС через асинхронность (Kafka) и вынесение логики (СРС). |
| **Недостаток** | **Гибридная архитектура / Технологический зоопарк.** Поддерживаются старые и новые стеки, что усложняет обслуживание. | Четкое разделение ответственности: новые системы обрабатывают логику и интеграцию. |
| **Риск** | **Неготовность Интернет-банка к 24/7.** Команда ИБ утверждает, что требования NF.1/NF.2 пока невыполнимы. | Перенос **ответственности за доступность** на новый API Gateway и СОЗ. Настройка **автоматического переключения на резервный ЦОД**. |
| **Риск** | **Несовместимость Интернет-банка с Kafka.** Требуется переработка для полноценного использования брокера. | В MVP использовать Gateway для временной синхронной связи с ИБ, переводя основную обработку в асинхронный СОЗ. |
